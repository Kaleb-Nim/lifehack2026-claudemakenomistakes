# Phase 2 — UI Design Contract

> Visual and interaction contract for Phase 2: Real-time voice, scripted brain.
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope note — read this first

Phase 1's visual design (`components/Onboarding.tsx`, `app/globals.css`, `lib/merchant-data.ts`) is
**final and out of scope**. This is a 24h hackathon page whose only output is a recorded 1080p
video; there is no design system to author here, only new interaction behaviour layered onto an
existing, immovable stage. This document does **not** propose new layout, tokens, palette, or type
scale for the stage — it documents what already exists (so the checker has a baseline) and then
specifies, prescriptively, only the **new** surfaces and state machines Phase 2 introduces:

1. Orb states driven by real Realtime session events (adds a `connecting` state)
2. Live caption bubble fed by real input transcription (replaces the fixed-text typewriter)
3. Agent line swap timing (verbatim script line, timed to real audio start)
4. Operator beat indicator / teleprompter (new, operator-only)
5. Connection/fallback status chip (new, operator-only)
6. Mic permission moment
7. Keyboard affordances (`M` / `R` / `Esc` added to existing `→`/`←`/Space)

Everything the camera sees must match the existing Modernist tokens (Archivo, single accent
`#ec3013`, line-SVG icons). Everything operator-only must be visually unmistakable as chrome (not
page content) and must not exist in the DOM under `?record=1`.

**Concurrency note:** session `merchant-25` owns `app/globals.css` and the `.stage` transform line
in `Onboarding.tsx` concurrently (Phase 1 visual bug fixes — cards overflow, stage centering).
Phase 2 must not touch those beyond the one additive CSS rule called out below (`.orb.connecting`),
and must not "helpfully" fix the two bugs (cards overflow, stage centering) named in CONTEXT.md —
they are not this phase's to fix.

## New Surfaces & Interaction Contract

### 1. Orb states (VOICE-02)

The existing orb derivation (`Onboarding.tsx`) is:
`orbState = live ? "speaking" : typing ? "listening" : frame.orb`, rendered as class
`orb {orbState}{orbState !== "idle" ? " live" : ""}`.

Phase 2 keeps this exact derivation *shape* — CONTEXT.md is explicit that real session events
must "feed that same derivation rather than a parallel one" — but swaps the triggers for real
events and inserts one new state ahead of it:

| Priority | Condition | orb class | orb-label | Camera-facing? |
|---|---|---|---|---|
| 0 (pre-tap) | No session ever started this page load | `idle` (existing) | Frame A's existing copy, unchanged | Yes |
| 1 | Orb tapped / owner starts talking → mic permission + ephemeral-key mint + WebRTC handshake in flight, session not yet ready | `connecting` (**new**) | `"Connecting…"` (new microcopy — operational, not brief copy) | Yes |
| 2 | Session ready; agent audio actively playing (`response.audio.delta`…`response.audio.done` / `output_audio_buffer.started`…`.stopped`) | `speaking` (existing) | current beat's existing `orbLabel`/`"Speaking"` (unchanged) | Yes |
| 3 | Session ready; owner speech active (`input_audio_buffer.speech_started` → `speech_stopped` + 400 ms settle, CONTEXT.md) | `listening` (existing) | `"Listening to you"` (existing string, reused) | Yes |
| 4 | Session ready; nobody currently talking (gap between the agent's line finishing and the beat advancing, or before the owner starts a turn) | `idle` (existing visual, reused) | `"Your turn — go ahead"` (new microcopy) | Yes |
| 5 | Session dropped mid-beat, silently fallen back to scripted mode (see §5) | falls back to Phase 1 behaviour: `frame.orb` / `frame.orbLabel` exactly as today | scripted `frame.orbLabel` (existing, unchanged) | Yes |

**Why state 4 is not just `frame.orb`:** `frame.orb` is a per-beat *scripted-timing* hint (mostly
`"speaking"` for beats C–G) that assumed a fixed-duration typewriter/timer was always running. In
real session mode there are genuine silent gaps (waiting on VAD, a pill tap, or nothing at all)
where showing a pulsing "speaking" orb while no audio plays would read as broken on camera. State 4
resolves this: during any silent gap, always show the plain `idle` visual with the new
`"Your turn — go ahead"` label, regardless of what `frame.orb` says. `frame.orb`/`frame.orbLabel`
are used only as the *fallback-mode* value (row 5), exactly as Phase 1 already renders them.

**`connecting` implementation — the one CSS exception:** reuse every existing keyframe
(`qhalo`, `qbeat`, `qmorph3`, `qspin`/`qspinr`) unchanged. Add exactly one additive rule to
`app/globals.css` (coordinate with `merchant-25` before landing — it is a pure addition, not a
modification of any existing line):
```css
.orb.connecting { --beat: 2.2s; }
```
Render `connecting` with the `live` class (same as `speaking`/`listening` already get today), so
the orb visibly "does something" for the ~0.3–2 s handshake instead of sitting frozen — `2.2s` is
slower than `speaking` (`1.5s`) and `listening` (`0.85s`) so a human glancing at the screen reads it
as "working," not "talking."

**Failure paths (mic denied, key mint fails, ICE fails, no `OPENAI_API_KEY`):** per CONTEXT.md,
none of these ever surface an error on the stage. They fall straight to §5 (silent fallback to
scripted mode at the current beat). The *operator* sees this via the status chip (§5), never the
camera.

### 2. Live caption bubble (VOICE-03)

Existing: `.caption`/`.caption-text` renders a fixed hardcoded string via `useTypewriter` at a
constant 28 cps with a blinking `.caret` (`qcaret` keyframe, unchanged).

`?mode=scripted` keeps this exact typewriter behaviour, unchanged, verbatim (VOICE-05).

Real-session mode replaces the *data source and reveal mechanism* only — the DOM structure, CSS
classes, caret element and animation are unchanged:

| Behaviour | Contract |
|---|---|
| Growth | Append each `input_audio_transcription` delta to `.caption-text` as it arrives — no artificial cps pacing (the owner's own speech rate is the pacing). The `.caret` element stays mounted and blinking (`qcaret`, unchanged) for the full duration of the owner's turn. |
| Correction / ASR revises a word | The ASR may replace a trailing partial (e.g. ASR rewrites "too" → "two"). Re-render the corrected text in place on the next delta — no strikethrough, no flash, no CSS transition on the text node (a transition on a shortening/lengthening string reads as a stutter). Only the caret continues to blink; the text swap itself is instantaneous. |
| Silence mid-turn | If the owner pauses (>1.5 s with no new delta) while `speech_started` is still open, keep the last partial text visible exactly as-is, caret still blinking. No "…" placeholder, no dimming, no truncation. |
| Finalization | On `input_audio_buffer.speech_stopped`: freeze the text at the final transcript, remove the `.caret` element (stop blinking), hold for the 400 ms settle delay (CONTEXT.md), then unmount the bubble when the beat advances and the agent line swaps in — same lifecycle Phase 1 already has for the typewriter caption. |
| Overflow (owner talks much longer than the scripted line) | No new clipping/scroll machinery. The bubble keeps its existing `max-width: 640px` and `text-wrap: pretty` and grows vertically like normal text reflow. Accepted risk, not engineered against — a single beat is a 5–30 s turn, and the centre column has vertical headroom below the orb. Do not add `overflow`/`line-clamp` here (that would silently hide real owner speech, which is worse than a taller box on camera). |
| Empty / discarded turn | Per CONTEXT.md's minimum-speech-duration guard (~1.2 s): if the VAD-measured turn is shorter than the guard, discard the buffered transcript entirely and never render a caption bubble for it (avoids a one-word flash for a cough or "mm"). |
| Transcription failure | If `speech_started`/`speech_stopped` fire but no transcript delta ever arrives, render nothing in the caption region — the beat still advances on VAD alone (SCRIPT-04: the transcript is decorative, never gating). |

### 3. Agent line — verbatim swap timing (SCRIPT-02, locked decision)

`.agent-line` always renders the current beat's exact script string from `lib/agent-script.ts` —
**never** the model's output transcript, even if the model's audio drifts a word. This is locked in
CONTEXT.md; do not build a path that ever binds `.agent-line` to a Realtime transcript event.

| Moment | Contract |
|---|---|
| Beat entry (`response.create` fires with the verbatim instructions) | `.agent-line` does **not** change yet. Leave the previous state visible so there is no blank flash before audio starts (TTS synthesis has latency). |
| First audio frame (`response.audio.delta` / `output_audio_buffer.started`) | Swap `.agent-line` to the current beat's script line **and** transition the orb to `speaking` in the same tick, so text and "mouth open" appear together with no lag. Reuse the existing remount-on-`key={agentLine}` + `fade 0.5s ease-out` treatment unchanged. |
| No audio within ~2 s of `response.create` | Treat as a dropped session (§5): fall back to scripted mode, which renders `frame.agentLine` immediately via the existing Phase 1 path — the screen is never left blank. |
| Model's own output transcript | Logged to the operator-only debug surface only (see §4's teleprompter, optional debug line) — never rendered as `.agent-line`. |

### 4. Operator beat indicator / teleprompter (VOICE-06, new)

Purpose: a prompt for the person on camera (the owner needs their next line far more than the
agent does — CONTEXT.md) plus a live/connection readout for the operator.

| Property | Contract |
|---|---|
| Content | `Beat {n}/{N}` · the **owner's** next scripted line (pulled from the beat's `caption`/expected-turn field in `lib/agent-script.ts`) · a mic-state glyph (live / muted) · a connection dot |
| Placement | `position: fixed; left: 16px; bottom: 16px; z-index: 9999` on the **viewport**, not the `.stage` — anchored in the letterboxed margin outside the scaled 1920×1080 stage so it can never overlap stage content. The margin exists only when the viewport aspect ratio differs from 16:9 — **not** whenever `scale < 1`. The fit is `min(w/1920, h/1080)`; on a 16:9 viewport both ratios are equal, the stage fills both axes, and there is no leftover on either. Measured: 2560x1440 gives scale 1.333 and zero margin; 1366x768 gives scale 0.711 and 0.3px. Every 16:10 viewport yields 32-66px vertically. The component must therefore compute the band at runtime — `innerHeight - 1080 * min(innerWidth/1920, innerHeight/1080)` — and not assume one exists. |
| Visual language | Deliberately **not** on-brand: dark translucent panel (`rgba(20,20,20,0.88)` background, `#fff` text), `var(--font-mono)` (reuses the existing mono token so it reads as system chrome, not stage content), `13px`, `10px 14px` padding, `8px` radius, `box-shadow: 0 4px 16px rgba(0,0,0,0.4)`, max-width `360px`. Never uses `--color-accent` or any stage neutral — this is the "operator can never mistake it for page content" requirement. |
| Connection dot | 8px circle, non-brand palette so it's never confused with the accent: green `#2ecc71` connected/live, amber `#f5a623` connecting, grey `#888` scripted/fallback, red `#e74c3c` error/denied. |
| Mic glyph | Existing mic icon with a slash overlay when `M` (mute) is toggled — the only visible feedback for the mute key (see §7). |
| Overflow / long-text | Owner's next line can run long (Frame B's caption is ~400 chars). Truncate the teleprompter's preview to the first **180 characters + "…"** — explicit rule, not silent clipping. This is an operator aid; the operator is assumed to have the full script on paper or a second monitor. |
| Zero / last beat | At the final beat (G), there is no "next line" — render `"— end of script —"` rather than a blank line. |
| Empty / script load failure | If `lib/agent-script.ts` fails to provide beats at all, render `"Script unavailable"` rather than a blank or crashed panel. |
| `?record=1` | Not mounted at all (`{!isRecordMode && <Teleprompter />}`) — absent from the DOM, not merely hidden, so it never appears in a screenshot, recording, or DOM inspector during the take. |

### 5. Connection / fallback status chip (VOICE-06, new, operator-only)

| Property | Contract |
|---|---|
| Visual language | Same "system chrome" family as the teleprompter (dark panel, mono font, non-brand palette) — deliberately distinct from the existing on-stage `.hdr-chip` (which uses `--color-neutral-200` + `--color-accent` dot) so the operator never confuses the two. |
| Placement | `position: fixed; right: 16px; top: 16px; z-index: 9999` on the viewport — mirrors the teleprompter's corner, keeps clear of the stage's own header chip and Go-live button. |
| Trigger | Appears only on a state *change*: WebRTC disconnect, ICE failure, missing/invalid key, mint failure, or mic permission denied. Copy: `"Voice dropped — beat {n} continuing in scripted mode · press R to retry"`. |
| Auto-hide | Disappears 4 s after a successful reconnect. |
| Intentional drop (`Esc`) | Copy becomes `"Scripted mode (Esc)"`, persistent (no auto-hide) — this was a deliberate operator choice, not a failure, so it should stay visible for the rest of the take. |
| `?record=1` | Not mounted — same absent-from-DOM rule as the teleprompter. |

### 6. Mic permission moment (VOICE-06)

- The orb tap (State A) is the **only** permission trigger — never requested on page load.
- Tap fires `getUserMedia` and the ephemeral-key mint concurrently; orb enters `connecting` (§1) immediately.
- **Operational requirement, not a UI mechanism:** because a native browser permission dialog must
  never be the first thing on camera (CONTEXT.md), the operator must do one silent rehearsal tap
  *before* rolling the camera for the take, so the origin already has a granted permission by
  record time. Document this in the Phase 4 recording checklist — the component cannot suppress
  the browser's own permission chrome if it does appear.
- If permission is denied (or was previously denied and the browser silently rejects): no error
  surfaces on stage. Falls straight to §5's silent fallback, with the status chip's copy specifically
  reading `"Mic permission denied — scripted mode · press R to retry"` (a distinct copy variant of
  the general drop message, since the operator's fix is different — check OS/browser mic
  permissions, not the network).

### 7. Keyboard affordances (VOICE-06)

| Key | Action | Visible affordance? |
|---|---|---|
| `→` | Force-advance beat (existing meaning, unchanged) | None on stage (existing behaviour) |
| `←` | Back (existing meaning, unchanged) | None on stage (existing behaviour) |
| `M` | Mute mic | None on stage. Confirmation only via the teleprompter's mic glyph (§4) — operator-only. |
| `R` | Repeat current agent line / re-attempt a dropped session | None on stage. The status chip's copy is the only feedback ("press R to retry"). |
| `Esc` | Drop to scripted mode deliberately | None on stage. Status chip switches to the persistent "Scripted mode (Esc)" copy (§5). |

None of these five keys have any camera-facing affordance — by design, since none are meant to be
seen by the viewer of the finished video. All five must no-op safely (no throw, no visible glitch)
when there is no active session to act on (e.g. pressing `M` before ever tapping the orb).

> approval with corrected element kinds. The first pass classified the orb, caption, agent line and
> status chip as plain `static-content` and surfaced only overflow/long-text for them; they are

### Operational constraints this section surfaces (for Phase 4's recording checklist)

Two rows above resolve to a *rehearsal* obligation rather than code, and will be invisible if they
are not written into the shoot checklist:

1. **Do one silent orb tap before rolling.** The browser's native permission dialog cannot be
   suppressed by the component; granting the origin beforehand is the only way it never appears on
   camera (§6).
2. **Record in a NON-16:9 window.** The teleprompter and status chip live in the letterboxed
   margin outside the scaled stage, and that margin exists only when the viewport's aspect ratio
   differs from 16:9 — size and scale are irrelevant. Any 16:9 window kills the overlays, including
   2560x1440 (scale 1.333, zero margin) and 1280x720, not just 1920x1080. A "is the scale below 1?"
   check does **not** catch this: 1366x768 is 16:9 at scale 0.711 with 0.3px of margin, while
   2560x1440 is 16:9 above 100% scale with none.

   Measured gutters (top/bottom):

   | Viewport | Scale | Margin | Verdict |
   |---|---|---|---|
   | 1920x1080 · 16:9 | 1.000 | 0 | overlays have nowhere to go |
   | 2560x1440 · 16:9 | 1.333 | 0 | overlays have nowhere to go |
   | 1366x768 · 16:9 | 0.711 | 0.3px | overlays have nowhere to go |
   | 1512x982 · 16:10 | 0.787 | 65.8px | works |
   | 1440x900 · 16:10 | 0.750 | 45px | works |
   | 1280x800 · 16:10 | 0.667 | 40px | works |
   | 1024x640 · 16:10 | 0.533 | 32px | works |

   Authoring on any MacBook 16:10 viewport is fine. The honest runtime check, if the overlays need a
   guaranteed band of `N` px, is `innerHeight - 1080 * min(innerWidth/1920, innerHeight/1080) >= N`
   — evaluated live, never inferred from window size (§4).
